# jevcumber v0.2 — four milestones

**Date:** 2026-09-22 · **Status:** approved (conversation) · **Builds on:** `2026-09-18-jevcumber-design.md`

Everything here keeps the core rule: **code enumerates, Jev selects, code executes.** No question
ever asks Jev to produce text.

## Milestone A — everything deterministic in CI

### A1. Pinned expectations
Today a `Then` with no literal (`Then I see an article about bagels`) is a `semantic` assertion:
judged live by Jev on every run, so it needs the API key and fails under `--frozen`.

New behaviour when such a step is resolved (non-frozen run): one Jev request carries **two**
questions over the same state:
- `holds` (Noul, as today): does the page show what the expectation describes?
- `evidence` (Choice): which one item in `page.evidence` best shows the expectation is met, or
  `none` if no single item does.

`page.evidence` is built by code from the page — the page title, visible `h1`–`h3` text, and the
names of links and buttons — deduplicated by text (first occurrence wins), each trimmed to 80
characters (a heading over 80 characters is dropped rather than truncated, since a truncated
heading could never `getByRole('heading', { name, exact: true })` back to itself), capped at 40
items ranked by word overlap with the step (`mostRelevant`, title/heading winning ties), and sent
as `{ id, text, kind }` where `kind` is `'title' | 'heading' | 'link' | 'button'`.

Outcome: only `title` and `heading` evidence is ever pinned to — a link or button name is not
something a `Then` step is really "about", so it settles which evidence item answers the question
but is never itself pin-worthy.
- `holds ≥ 0.8`, `evidence ≠ none`, its `kind` is `title` or `heading`, and confidence ≥ 0.6 → the
  step passes **and** its lockfile entry becomes `{ kind: 'assert', assertion: { form:
  'title_contains' | 'heading_visible', value: <evidence>, pinned: true } }`. Later runs replay it
  as a plain Playwright check (`toHaveTitle` / a `getByRole('heading', { name, exact: true })`
  visibility check), frozen or not.
- `holds ≥ 0.8` and no evidence, or evidence whose `kind` is `link`/`button` — passes; entry stays
  `{ form: 'semantic' }` (live, as today).
- `holds < 0.8` → fails as today.

`pinned: true` is informational (reporter shows `✓ … (pinned to "Michelle Obama")` on the run that
pins; `explain` shows it later). Healing: if a pinned assertion fails on a later non-frozen run, the
step is **re-judged** (not immediately failed): jevcumber runs the live judgment again; if it holds
and re-pins, the entry is re-pinned to the new evidence and the step reports `healed`; if it holds
but finds nothing to pin, the entry becomes `{ form: 'semantic' }` and the step still reports
`healed`, with the note "no longer pinned: needs Jev under --frozen"; if it doesn't hold, the step
fails with both the original failure and the re-judge's error in its detail (`pinned check failed
(<original>); re-judge: <again>`). Under `--frozen` a failing pinned assertion is a plain failure,
never re-judged (no API calls happen under `--frozen`).

### A2. Page-sourced values
Candidates for **`click`/`check`/`uncheck` targets** are unchanged (elements). Candidates for
**`fill`/`select` values** and for the **`click` target when no element matches by name** are
extended: in addition to step literals, the `input_text` question is offered `page_text` candidates —
headings and link/button names (same evidence list as A1, ids `p1…`). For `click`, the element
question already lists links by name, so "I click the link to his wife" is answered by the
element question alone once the instructions say the step may *describe* the target rather than
name it.

Guardrail: an answer that selects a page-sourced candidate (id `p…`) must reach **0.75**
confidence (literals keep `--min-confidence`, default 0.6). Below that, ambiguous as usual, with
the candidates listed.

A page-sourced value is fixed in the lockfile the first time it resolves, exactly like any other
resolution; if the page text it was drawn from later changes, the cached value is still replayed
as-is until the entry is invalidated (its locator goes stale) or the lockfile is rebuilt with
`--update`. Re-resolving a page-sourced value automatically when the page text drifts is deferred
past this milestone.

Amendments from live tuning (2026-09-22): the evidence gate uses the chosen item's *probability*
(several items can legitimately show the same thing, which spreads probability and lowers the
distribution's confidence); the question prefers the title or a heading over links/buttons; evidence
whose `kind` is `title` is pinned as a `title_contains` assertion (`expect(page).toHaveTitle`) since
a title is not visible text, and evidence whose `kind` is `heading` is pinned as a `heading_visible`
assertion (`page.getByRole('heading', { name, exact: true })`) rather than a plain `text_visible`,
so a replayed pin only matches an actual heading, not any text that happens to equal it elsewhere on
the page. Pinned entries store the evidence probability as `confidence`. The `navigate` option now
says a Then step reading "I am on the X page" is a check, not navigation.

### A3. Lockfile v2
`"version": 2`. Entries gain `confidence` (number, the resolution's confidence) and may carry
`pinned`. A v1 lockfile is loaded as-is and rewritten as v2 on the next non-frozen save; `--frozen`
accepts both. Any other version is an error.

## Milestone B — vocabulary and failure evidence

### B1. New step kinds
| kind | executor | needs |
| --- | --- | --- |
| `hover` | `locator.hover()` | element |
| `clear` | `locator.fill('')` | element |
| `upload` | `locator.setInputFiles(path)` — path literal from the step, resolved relative to the feature file; `input[type=file]` elements are collected with role `file` | element + value |
| `scroll` | `locator.scrollIntoViewIfNeeded()` | element |
| `wait` | wait for a literal text to appear (`expect(getByText).toBeVisible`, 15 s) when the step has one; otherwise wait `N` seconds when the step has a number (max 30); otherwise `page.waitForLoadState('networkidle')` | value (optional) |

`KIND` gains these five options with `what`/`examples`. `fill` on a `select` element is executed as
`select`. `select` accepts an option **index** when the value is a number and no option label/value
matches.

### B2. Failure evidence
For every step that ends `failed`, `ambiguous`, or `undefined`, the runner writes
`jevcumber-report/<feature-basename>/<scenario-slug>/<step-index>-<status>/` containing
`screenshot.png` (full page) and `snapshot.json` (the last snapshot Jev saw, or a fresh one if the
step never resolved). The reporter prints `evidence: <dir>` under the step. `--report-dir` changes
the root; `--no-report` disables. `--trace` records a Playwright trace per scenario and keeps
`trace.zip` in the scenario's report directory only when a step did not pass.

## Milestone C — speed and project ergonomics

### C1. Parallel scenarios
One Chromium for the run. `--workers N` (default `min(os.availableParallelism(), scenarios)`);
each worker pulls the next scenario from a queue and runs it in its own browser context. Lockfiles
are in-memory objects shared across workers in the one process; `set`/`touch` are synchronous so no
locking is needed; saved once at the end as today. `--headed` forces `--workers 1`.

### C2. Console output under parallelism
The console reporter buffers each scenario's lines and prints the whole block when the scenario
finishes (feature header printed once per feature, when its first scenario completes). While
scenarios run and stdout is a TTY, one status line is redrawn on stderr:
`3/12 scenarios · 2 running · 1 failed`; cleared before each block is printed and at the end.
Non-TTY output (CI) gets blocks only. `--workers 1` output is identical to v0.1.

### C3. One-round-trip snapshots
`collect()` also computes, in the page, whether each candidate's `testid`, `label`, `placeholder`,
`text`, and `role+name` (using the module's own role/name computation) occur exactly once. Only the
**first** spec that is unique in-page is then verified with a single Playwright `count()`; the
`repeated` pre-filter goes away. Result: ≤ 1 round-trip per candidate instead of ≤ 5.

### C4. Config file
`jevcumber.config.js` / `.mjs` found by walking up from the cwd (`--config <path>` overrides).
Default export:
```js
export default {
  baseUrl: 'http://localhost:3000', workers: 4, tags: 'not @wip', minConfidence: 0.6,
  reportDir: 'jevcumber-report',
  hooks: {
    async beforeScenario({ page, scenario, baseUrl }) {},   // e.g. log in, seed data
    async afterScenario({ page, scenario, results }) {},
  },
};
```
CLI flags override config values. Hook errors fail the scenario (all steps `skipped`, a synthetic
`failed` line "beforeScenario hook: <message>").

### C5. Reporters
`--reporter console|json|junit` (repeatable) and `--output <file>` for the file reporters
(default `jevcumber-report/results.json` / `results.xml`).
- `json`: Cucumber's classic JSON formatter shape (`[{ uri, name, elements: [{ name, steps:
  [{ keyword, name, result: { status, duration, error_message } }] }] }]`) — consumed by existing
  dashboards and the `cucumber-html-reporter` family. Statuses map: passed/healed → `passed`,
  ambiguous/undefined → `undefined`, failed → `failed`, skipped → `skipped`.
- `junit`: one `<testsuite>` per feature, one `<testcase>` per scenario; a non-passing scenario
  gets `<failure message="…">` with the failing step and detail.
Step durations are recorded (`StepResult.durationMs`).

## Milestone D — tooling and docs

### D1. `jevcumber explain <paths…>`
No browser, no API. For each scenario, prints each step with its lockfile resolution in plain words
(`fill "Search Wikipedia" with "bagel" then Enter · confidence 0.97`, `assert text "Michelle Obama"
is visible (pinned)`, `live: judged by Jev each run`, `not in lockfile`). Exit 1 if any step lacks an
entry (useful in PR checks alongside `--frozen`).

### D2. `--record-eval <dir>`
For every step that calls Jev, write `<dir>/<feature-basename>/<scenario-slug>/<step-index>.json`
with `{ step, state, questions, answers, outcome }` — exactly what the resolver saw and decided —
so a misresolution can be reproduced offline and turned into an eval fixture.

### D3. Cookbook
`scripts/cookbook.ts` reads every fixture and example feature plus `fixtures/expected.ts` and
generates `site/cookbook.html` (same visual language as the landing page): each known-good step
phrasing grouped by kind, with what it resolves to. Linked from the landing page nav and the README.
`npm run cookbook` regenerates it; `deploy:site` runs it first.

## Cross-cutting
- Every new question's wording is tuned with `e2e/resolve-eval.test.ts` against live Jev before it
  is committed; fixture features are added for each new kind and for pinned expectations.
- The README, `site/index.html` (install/CLI copy), and the v0.1 spec's CLI section are updated with
  each milestone. All four milestones ship together as **0.2.0** (one release; the interim `v0.2.0` tag cut after
  Milestone A is recreated at the final commit).
